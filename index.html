03. Engineering "Saves"

System Optimization

The 95% Latency Kill (Question Management Bank)

The Problem

A synchronous route processing 10k+ exam/assessment question documents was blocking the Node.js event loop for 5 minutes (300 seconds).

The Solution

Refactored it into an asynchronous pipeline that splits the documents into chunks and processes them in parallel, so the event loop stays free.

95% REDUCTION

Processing time dropped from 300 seconds to 15 seconds.

Frontend Scalability

The "1500-Cell Problem" (Attendance Control App)

The Problem

Data-heavy attendance-tracking screens with 1,500+ clickable/anchor-based cells were causing DOM lag and interaction latency.

The Solution

Implemented table virtualization in React.js/Next.js, rendering only visible rows to cut DOM overhead.

PERFORMANCE STABLE

Massive reduction in DOM nodes and stable "Time to Interactive" (TTI).

Architecture

Multi-Tenant RBAC (IBMS)

The Methodology

Used Event Storming and Event Modeling to map IBMS (Integrated Business Management System) — an HRM-style workforce/business platform serving FUNIBER's constituent organizations.

The Solution

Architected multi-schema data isolation per organization plus a runtime-configurable RBAC system.

ZERO LEAKAGE

Strict data isolation across every constituent organization on the platform.

Domain Modeling

Modeling a Jira/Asana/Miro Hybrid (Padmasana)

The Problem

The org needed an internal project/task-management and collaboration tool adapted to its own workflows — functionally comparable to Asana, Miro, and Jira.

The Solution

Ran event modeling and event storming to map the domain, then built Padmasana as a modular monolith — module separation enforced at the schema level — with Socket.IO-based real-time collaboration.

MODULAR MONOLITH

Clean, layered architecture without the operational overhead of a microservices split.
